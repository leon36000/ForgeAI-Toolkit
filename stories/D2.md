# D2 — Adoption au déploiement : brancher l'existant au lieu de le redéployer

## Défaut (prouvé par exécution, voir reviews/D2/evidence/RED.txt)

Le moteur de découverte D1 est livré (`network/discover.py`, `inventaire()`, 10 signatures,
exposé par `forge node discover`). **Le chemin de déploiement ne le consulte jamais** :

    deploy/compose.py  consulte l'inventaire : False
    deploy/k3s.py      consulte l'inventaire : False
    compose_up(compose_file: Path, services: list[str] | None = None) -> None
    k3s_apply(manifest: Path) -> None

Aucun paramètre ne transporte « ce qui est déjà là ». Un utilisateur ayant déjà un redis, un
postgres ou un qdrant en service les voit **redéployés** : conteneur recréé, configuration
écrasée. C'est la violation directe de la règle permanente du produit — *adopter l'existant,
jamais réinstaller ni écraser*.

## Décision d'architecture (Kimi-K3, ADR complet en reviews/D2/evidence/ADR.md)

1. **Point d'insertion = construction du PLAN** (`planner/assemble.py`). Le plan sort annoté ;
   renderers, santé, secrets et CLI ne font qu'exécuter une décision déjà prise.
   - Décider au RENDU obligerait à implémenter deux fois (compose ET k3s) avec divergence
     possible, et le plan mentirait aux autres consommateurs.
   - Décider au DÉPLOIEMENT laisserait sur disque un artefact décrivant une infra que nous ne
     gérons pas : tout `compose_down` ultérieur deviendrait destructif sur l'existant.

2. **Un seul champ** : `ServiceSpec.adopted_endpoint: Optional[str] = None`, en fin de dataclass.
   La présence de l'endpoint EST le marqueur d'adoption — un booléen séparé pourrait se
   contredire avec lui. Défaut `None` = comportement actuel inchangé. Validation stricte
   `hôte:port` dans `__post_init__` : cette valeur atteint le YAML en brut.

3. **Le NOM du service reste la clé, seule la résolution change.** Une adoption qui changerait
   la clé casserait chaque brique consommatrice. Compose : le workload adopté est omis, et
   chaque dépendant reçoit `host.docker.internal:<port découvert>` + `extra_hosts:
   ["host.docker.internal:host-gateway"]`. **L'existant prime sur le catalogue** : c'est le port
   découvert qui est utilisé, pas le `host_port` du catalogue.

4. **K3s : REFUS explicite.** L'inventaire ne rend aujourd'hui que `127.0.0.1:<port>`, inutilisable
   comme cible d'`Endpoints` depuis un pod. Le renderer lève une erreur nommée plutôt que de
   produire un câblage faux qui échouerait à l'exécution.

5. **Jamais d'adoption implicite** : uniquement sur `--adopt <nom>=<endpoint>`. Un conflit non
   arbitré échoue net, sans rien démarrer ni écrire.

## Critères d'acceptation (testables)

- **CA-1** : plan avec un service `adopted_endpoint="127.0.0.1:6379"` → le service est
  **totalement absent** de la section `services:` du compose rendu.
- **CA-2** : un dépendant de ce service reçoit `host.docker.internal:6379` — le **port découvert**,
  **pas** le `host_port` du catalogue.
- **CA-3** : dès qu'un service est adopté, le dépendant porte
  `extra_hosts: ["host.docker.internal:host-gateway"]`.
- **CA-4** : `render_k3s` sur un plan contenant un service adopté lève une erreur explicite
  **avant toute écriture**.
- **CA-5** : `ServiceSpec(adopted_endpoint="pas_un_endpoint")` lève `ValueError` avec le code
  du motif de rejet.
- **CA-6** : **non-régression** — avec `adopted_endpoint=None` partout, le compose et le k3s
  rendus sont **identiques octet pour octet** à ceux d'avant la story.
- **CA-7** : `--adopt` deux fois sur le même service → code de sortie non nul, message nommant
  le conflit.

## Ce que cette tranche NE fait PAS (limites assumées)

- **Pas de re-sonde TCP au déploiement.** Un service adopté mort n'est pas détecté par cette
  tranche ; c'est une story suivante (l'ADR la spécifie).
- **Pas de détection automatique.** L'endpoint est fourni explicitement via `--adopt` ; le
  branchement `inventaire()` → proposition automatique est la story D3 (UI).
- **K3s : refus uniquement**, aucune adaptation.
- **Couverture réelle** : sur les 12 briques déployables, **seules redis, qdrant et postgres**
  ont une signature de détection. litellm, TEI-embeddings, TEI-reranker, immudb, openbao,
  langfuse, llama-cpp-vulkan, cpu-zendnn et intel-openvino **ne sont pas détectables** —
  l'adoption ne les concerne pas tant que leurs signatures n'existent pas.

## Défaut découvert EN COURS de story (non prévu par l'ADR)

Le crew avait mal utilisé ses propres helpers de test : il adoptait `litellm` (le dépendant)
au lieu de `redis` (la dépendance). Erreur de test sans rapport avec le code — mais elle a
fabriqué un plan dont **tous** les services étaient adoptés, et révélé ceci :

    render_compose(plan 100% adopté) ->
      name: forgeai-minimal
      services:                       <- vide

    yaml.safe_load(...)["services"] is None

**Docker Compose refuse un fichier sans aucun service.** L'utilisateur ne l'aurait découvert
qu'au `docker compose up`, avec un message ne désignant pas la vraie cause. Ni l'ADR, ni la
story, ni mes critères d'acceptation n'avaient envisagé ce cas.

**Corrigé** (tranche 5) : `RienADeployerError` levée AVANT toute construction, portant le code
`ERR_ADOPT_RIEN_A_DEPLOYER` et la liste des services adoptés avec leurs endpoints. Le message
précise que **ce n'est pas une erreur de l'utilisateur** mais un état à lui signaler : tout est
déjà présent, il n'y a rien à déployer.

Trois cas vérifiés par exécution :
  tous adoptés     -> RienADeployerError nommant redis et qdrant
  1 adopté + 1 non -> rendu normal, services = ['litellm']
  aucun adopté     -> strictement inchangé

## Revue scellée tour 1 : REJECT 2/3 — objection FONDÉE

DeepSeek APPROVE, **Gemini REJECT**, **Grok REJECT** (3 vendors distincts, MiniMax le codeur
absent du panel). Objection critique concordante :

> CA-2 non implémenté : aucun code n'injecte `host.docker.internal:<port découvert>` dans les
> variables d'environnement des dépendants. Le test `test_CA2` ne couvre pas le CA-2 de la
> story : il vérifie seulement l'absence de redis dans `depends_on` — **un effet de bord**.

**L'objection est juste, et la faute est la mienne.** En découpant la story en tranches, j'ai
sorti le recâblage des variables d'environnement de la tranche 2 (« tranche suivante ») **sans
retirer CA-2 de la story**, puis j'ai déclaré CA-2 satisfait sur la foi de `depends_on == None`.

Conséquence concrète : l'état que j'allais merger **dégradait le produit**. Le workload adopté
disparaissait du compose, mais le dépendant ne savait plus où le joindre — `litellm` sans
`redis`. L'ADR l'avait pourtant écrit : *« une adoption qui casse le câblage est pire qu'un
redéploiement »*.

### Correction (tranches 7 et 8)

Recâblage réel des variables d'environnement, prouvé par exécution sur les formes du produit :

    LANGFUSE_HOST  http://langfuse:3000              -> http://host.docker.internal:3999
    DATABASE_URL   postgresql://u:pw@postgres:5432/db -> postgresql://u:pw@host.docker.internal:5555/db
    PIEGE_1        http://mylangfuse:3000            -> INCHANGÉ (pas de substitution dans un mot)
    PIEGE_2        langfuse_backup                   -> INCHANGÉ

Le port est celui **découvert** (3999, 5555), pas celui du catalogue (3000, 5432) : l'existant
prime, conformément à l'ADR.

4 tests ajoutés, dont un test **anti-faux-positif** explicite. Contrôle de mutation :
recâblage neutralisé -> `test_CA2_dependant_pointe_vers_endpoint_decouvert` et
`test_CA2_chaine_de_connexion_recablee` ROUGISSENT ; restauré -> 19 verts.
L'ancien test a été renommé `test_le_dependant_ne_reference_plus_le_service_adopte_dans_depends_on`
— il reste utile, mais il ne porte plus le nom d'un critère qu'il ne prouvait pas.

### Chemin mort retiré (qualité)

Le crew avait entouré le parsing de l'endpoint d'un `try/except (ValueError, AttributeError):
pass`. Prouvé inatteignable : les 4 formes invalides sont rejetées à la construction de
`ServiceSpec` (ERR_ADOPT_FORME / _HOTE / _PORT / _PORT_BORNES). Et s'il devenait atteignable,
il produirait **exactement le défaut que la revue venait de signaler** : dépendant non recâblé,
sans aucun message. Retiré, avec la justification en commentaire.
