# DOC-032 — Réconcilier la documentation publique avec l'état prouvé

Issue #283. Dernière story de la lane, volontairement traitée en dernier pour que la
documentation se réconcilie avec l'état **final et prouvé**, pas avec un état intermédiaire.

## 1. État mesuré

**5 sous-commandes documentées sur 21.** Mesure : extraction par AST des `add_parser("…")` de
`src/forgeai/cli.py` **portés par le sous-parseur racine** (21 commandes de premier niveau ;
compter aussi les imbriquées en donnerait 42, mais « forgeai node prepare » ne peut jamais
correspondre à « forgeai prepare », donc les compter produirait des anomalies indéfendables),
puis recherche de `forgeai <cmd>` dans les
25 fichiers de documentation (`README.md`, `AGENTS.md`, `MASTER-PLAN.md`, `CLAUDE.md`,
`Docs/**`, `CANON/**`). Seules `doctor`, `gpu`, `route`, `web`, `wizard` apparaissent.

**Volume documentaire total : 382 lignes** (README 77, AGENTS 126, MASTER-PLAN 145, CLAUDE 34)
pour un produit qui expose 21 commandes de premier niveau (42 en comptant les imbriquées),
une interface web, un serveur d'API, une chaîne de
déploiement Compose/K3s et une gouvernance de registres hachés.

**Aucune commande fantôme.** Point important pour le diagnostic : la documentation ne cite
aucune commande inexistante (hors `--help`). Le défaut n'est donc pas qu'elle **ment**, c'est
qu'elle **omet** — ce qui échappe à toute relecture, puisqu'il n'y a rien à contredire.

**Surface livrée par cette lane et absente de la doc** : `forgeai status`, `forgeai logs`,
`forgeai diagnostic`, le panneau opérateur web, le rate limiting, les en-têtes de sécurité, le
mode TLS explicite, les correlation IDs, la rédaction des secrets, le contrôle de complétude des
registres et le gate d'ancrage anti-rollback.

**`scripts/gate_docs.py` n'existe pas.** `tests/test_docs_consistency.py` existe mais ne couvre
qu'un seul sujet (la documentation des pilotes GPU, 4 tests) : rien ne détecte la dérive générale.

## 2. Décision de conception, et ce qui a été réfuté

### Réfutation 1 — « écrire la documentation manquante »
**Insuffisant seul, et voué à re-dériver.** Une documentation rédigée à la main pour 21 commandes
sera périmée à la prochaine commande ajoutée, exactement comme celle-ci l'est devenue. Le
livrable durable n'est pas un texte : c'est un **contrôle qui rend la dérive détectable**.

### Réfutation 2 — « un gate qui exige que TOUT soit documenté »
**Rouge dès le premier jour sur 16 commandes**, donc désactivé sous 48 heures — le même piège
que REG-029A avait identifié pour la complétude. La forme retenue est le **cliquet déjà prouvé
par REG-029B** : la dette est figée dans une base de référence versionnée, toute commande
**nouvelle** doit être documentée, et la base ne peut pas croître.

### Réfutation 3 — « générer la référence CLI automatiquement à chaque build »
Rejetée : une documentation générée à la volée n'est pas relue, et un fichier non versionné ne
peut pas servir de référence au cliquet. La référence est **écrite et versionnée** ; le gate
vérifie qu'elle correspond à la CLI réelle.

### Décision
Trois livrables, dont un seul est du texte :

1. **`Docs/reference/cli.md`** — référence des commandes, à commencer par celles que cette lane a
   livrées et par la surface de sécurité/exploitation, qui sont les moins devinables.
2. **`scripts/gate_docs.py`** — le gate : toute sous-commande de `cli.py` doit être documentée
   **ou** figurer dans une base de référence bornée. Une commande absente des deux fait rougir.
3. **Réconciliation des états chiffrés** du README avec la mesure (paquets complétés, entrées de
   registre), puisqu'un chiffre périmé est la forme de dérive la plus facile à croire.

## 3. TDAD

- **G1** toute sous-commande de `cli.py` est documentée ou baselinée — sinon ROUGE.
- **G2** une commande **nouvelle** ne peut pas être baselinée (la base est bornée) : ajouter une
  commande sans la documenter rougit, même en modifiant la base.
- **G3** la base ne peut pas croître par rapport à `origin/main`.
- **G4** une entrée de base **périmée** (commande supprimée, ou désormais documentée) rougit —
  sinon la base devient une couverture générale.
- **G5** le gate est réellement invoqué par `.github/workflows/gates.yml` (assertion sur la
  structure YAML, pas sur le texte).
- **G6** les commandes livrées par cette lane (`status`, `logs`, `diagnostic`) sont documentées —
  et le test échoue si la section disparaît.
- **G7** la source de vérité est la CLI, pas une liste recopiée : ajouter une commande à `cli.py`
  la fait apparaître dans le périmètre du gate sans toucher au gate.

## 4. Critères d'acceptation

- **CA1** `scripts/gate_docs.py` existe, est invoqué par la CI, et échoue sur toute commande ni
  documentée ni baselinée.
- **CA2** base de référence **bornée et non croissante**, vérifiée contre `origin/main` — même
  mécanisme que REG-029B, dont la propriété a été prouvée.
- **CA3** `Docs/reference/cli.md` documente au minimum la surface livrée par cette lane et la
  surface de sécurité/exploitation.
- **CA4** les chiffres d'état du README correspondent à la mesure, ou n'y figurent plus.
- **CA5** suite complète verte (hors l'échec environnemental pré-existant de `tests/test_proc.py`,
  documenté et traité hors périmètre) ; couverture ≥ 85 %.

le dossier, exactement comme réécrire une ADR. Seuls les documents d'**état** ont été réconciliés.

ajouter une commande non documentée → rc=1 ; l'ajouter **aussi à la base** pour faire passer la PR

**Défaut trouvé et corrigé pendant la livraison** : la règle de borne était imbriquée dans le bloc
`base_reference`, donc **muette sans `--base-ref-git`** — il suffisait d'élargir la base pour
passer. C'est le même défaut que le REJECT R1 de REG-029B, une story plus tard : une règle
présente mais suspendue à un argument optionnel. La borne est autoportante et l'est désormais
inconditionnellement ; **G2** le prouve sans aucune référence git.

**Mutations** : ré-imbriquer la borne → G2 rougit ; compter les sous-commandes imbriquées →
G8 + G9 rougissent.
