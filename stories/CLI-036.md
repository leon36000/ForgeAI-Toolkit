## 1. Problème (code réel)

`_loop_run` (cli.py ~l.1091) exécute chaque `--step`/`--until` via un runner sans aucun contrôle :

```python
def runner(cmd: str) -> int:
    return subprocess.run(shlex.split(cmd)).returncode
```

Un step (et ses enfants) peut **pendre indéfiniment** ; aucun timeout, aucune annulation propre,
aucun kill de l'arbre de processus. Un `bash -c "sleep 999 & wait"` laisse des orphelins.

## 2. Décision d'architecture (une justification par point)

1. **Emplacement — `src/forgeai/core/proc.py`, stdlib pur.** Isole la gestion de processus, testable
   sans coupler `loop.py`, exactement comme `core/_portable_lock.py` pour les verrous. Aucune dépendance
   externe (PAS de `psutil`) : la portabilité vient de branches `os.name`, la branche Windows étant
   prouvée par un mock déterministe (G5) et le chemin POSIX par exécution réelle.

2. **API du runner borné.** `timed_runner(timeout_seconds: float | None, grace_seconds: float = 5.0)
   -> Callable[[str], int]`. Le runner retourné a la signature `str -> int` (compatible avec l'injection
   existante) : il RETOURNE le code retour en sortie normale, et LÈVE `RunnerTimeoutError` (dépassement)
   ou `RunnerCancelledError` (SIGINT) — toutes deux sous-classes de `RuntimeError`. *Justif :* une seule
   surface, deux exceptions dédiées remontées telles quelles par `run_loop` jusqu'à `_loop_run`.
   `timeout_seconds=None` désactive tout timeout (non-régression stricte du chemin actuel).

3. **Groupe de process + kill d'arbre, EXACT par OS** (branche `os.name`) :
   - **POSIX** : `Popen(..., start_new_session=True)` (nouveau groupe/session, empêche la migration) ;
     kill via `os.killpg(os.getpgid(pid), SIGTERM)`, puis escalade `os.killpg(pgrp, SIGKILL)` après
     `grace_seconds`. *Justif :* le groupe capture l'arbre entier ; `start_new_session` évite d'atteindre
     un mauvais groupe.
   - **Windows** : `creationflags=subprocess.CREATE_NEW_PROCESS_GROUP` ; kill d'arbre par
     `subprocess.run(["taskkill", "/F", "/T", "/PID", str(pid)])`. *Justif :* `taskkill /T` énumère et
     tue l'arbre de façon documentée, là où `CTRL_BREAK_EVENT` n'affecte que la console attachée.

4. **Annulation SIGINT.** Le runner installe temporairement un handler `SIGINT` (thread principal)
   positionnant un `threading.Event`, boucle sur `p.wait(timeout=petit_intervalle)`, et sur event
   déclenche le kill d'arbre puis lève `RunnerCancelledError` ; le handler est TOUJOURS restauré
   (`try/finally`). *Justif :* évite qu'un `KeyboardInterrupt` atterrisse en plein syscall ; la frontière
   CLI-013 capture déjà tout `KeyboardInterrupt` résiduel en tête de `main()` (exit 130). *Alternative
   acceptable :* `try/except KeyboardInterrupt` autour de `wait()` qui tue l'arbre et lève
   `RunnerCancelledError` — au choix du crew si plus simple et prouvé équivalent par les tests.

5. **Surface CLI.** Nouvel arg `--timeout` (secondes, `float`, défaut `None`). Deux codes retour
   supplémentaires dans `_loop_run` : **14** (`RunnerTimeoutError`), **15** (`RunnerCancelledError`),
   distincts des 12 (LoopError) / 13 (budget) existants. *Justif :* défaut `None` = zéro régression ;
   codes distincts = diagnostic scriptable.

6. **Hors périmètre (suivi)** : `--grace` configurable en CLI, timeouts séparés step/until, annulation
   asynchrone multi-thread, signaux autres que SIGINT.

## 3. Stratégie de test TDAD (`tests/test_proc.py` — RED d'abord ; stdlib uniquement)

1. **Kill d'arbre réel (LE détecteur de fuite)** : step qui spawn un petit-enfant détaché, ex.
   `python -c "import subprocess,time; p=subprocess.Popen(['sleep','999']); open('PIDFILE','w').write(str(p.pid)); time.sleep(999)"`
   avec `timeout` court → après retour, `os.kill(pid_step, 0)` ET `os.kill(pid_petit_enfant, 0)` lèvent
   `ProcessLookupError`. POSIX-only (marqué `skipif os.name != 'posix'`).
2. **Chemin heureux** : step rapide `exit 0` → runner retourne le code, aucun kill (non-régression).
3. **Timeout** : step `sleep 999`, `timeout=1.0` → lève `RunnerTimeoutError`, durée mesurée `< 1 + grace + ε`.
4. **Annulation** : `SIGINT` envoyé pendant un step bloquant → arbre tué, `RunnerCancelledError`, pas de zombie.
5. **Portabilité** : tests `os.killpg`/`start_new_session` sous `os.name=='posix'` ; logique Windows
   (`taskkill`) testée par **mock de `subprocess.run`** avec `os.name` monkeypatché (couvre la branche
   `nt` sans Windows local, de façon déterministe). `proc.py` étant stdlib pur, il s'importe partout ;
   l'analyse de commande `shlex.split` (POSIX) reste un défaut pré-existant du runner, hors périmètre.
6. **Idempotence/robustesse** : kill d'un PID déjà mort → ni erreur ni faux positif ; `timeout=None`
   désactive le timeout (step long non tué, borné par le test) ; double SIGINT pendant la grâce → SIGKILL direct.
7. **CLI réel** : `cli.main(["loop","run","--max-iter","1","--step","sleep 999","--until","true","--timeout","1", ...])`
   → code 14 ; step rapide sans `--timeout` → comportement actuel inchangé (non-régression via la vraie
   sous-commande, pas seulement le runner isolé).

## 4. Critères d'acceptation (testables)

- **CA1** un step qui pend est tué au timeout ; aucun processus de l'arbre ne survit (assert déterministe).
- **CA2** `RunnerTimeoutError` → code CLI 14 ; `RunnerCancelledError` → code CLI 15.
- **CA3** `--timeout` absent / `None` → comportement identique à aujourd'hui (non-régression prouvée).
- **CA4** SIGINT pendant un step → arbre tué, sortie propre, pas de traceback (frontière CLI-013), pas de zombie.
- **CA5** branche Windows (taskkill) couverte par le mock déterministe G5 ; `proc.py` stdlib pur
  (importable partout, test AST) ; portabilité `shlex` du runner pré-existante et hors périmètre.
- **CA6** `core/proc.py` stdlib pur, sans import `forgeai.*` ni dépendance externe (test AST).
- **CA7** suite complète verte, no-stub, couverture ≥ 85 %.

## 5. Risques

- Windows `taskkill /T` non atomique (process créé entre énumération et kill) — assumé, documenté.
- Course `wait()`/kill : kill superflu mais idempotent (paré).
- SIGKILL non interruptible (syscall bloquant) peut dépasser le budget — borne de grâce documentée.
- Réutilisation de PID entre mort et kill — atténuée par latence + escalade rapide sur le groupe.
- SIGINT ré-entrant pendant le kill — handler restauré en `finally` ; double SIGINT → SIGKILL direct.
