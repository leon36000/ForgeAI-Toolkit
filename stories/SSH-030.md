# SSH-030 — `SshRunner` aplatit silencieusement tout argv contenant des espaces

Trouvé en pilotant `forgeai node discover` **contre du vrai matériel distant** (PC3 : NVIDIA,
PC4 : AMD, aucun des deux avec `docker`) — pas en lisant le code. Les deux nœuds, pourtant
matériellement différents, rapportaient le **même résultat identique** (`docker ✓`, `nvidia ✓`),
qui se trouvait correspondre exactement à l'environnement de la machine orchestratrice.

## 1. État mesuré

`discover.py:80` teste chaque binaire via :
```python
runner.run(["sh", "-c", 'command -v "$1"', "sh", binaire])
```
5 éléments d'argv, dont le 3ᵉ contient des espaces et des guillemets. Ce motif est **correct**
pour `SubprocessRunner` (local, `subprocess.run(argv, shell=False)` préserve l'argv réel), mais
**faux** pour `SshRunner` : `remote_probe.py:106-131` ajoute cet argv tel quel après `--` dans la
commande `ssh`, laissant OpenSSH le transmettre.

**Preuve au niveau du protocole** (`ssh -v`) :
```
debug1: Sending command: sh -c command -v "$1" sh docker
```
OpenSSH **rejoint les éléments d'argv avec un simple espace, sans les re-quoter**, et transmet
cette chaîne unique au shell distant. Le shell distant y voit alors `-c` suivi du seul mot
`command` comme script — tout le reste devient des paramètres positionnels sans effet. Reproduit
sans réseau ni matériel distant particulier, en rejouant l'argv réel puis l'aplatissement
prouvé par `-v` à travers un vrai `/bin/sh` local :

| Test | rc | stdout |
|---|---|---|
| argv actuel, binaire `docker` (absent du nœud réel) | **0** | vide |
| argv actuel, binaire `nvidia-smi` (présent sur PC3) | **0** | vide |
| même script correctement re-quoté, `docker` | **127** | — |
| même script correctement re-quoté, `nvidia-smi` | **0** | `/usr/bin/nvidia-smi` |

**`command -v` mal aplati renvoie systématiquement 0 avec une sortie vide, quel que soit le
binaire testé.** `node discover` déclare donc TOUT comme installé sur TOUT nœud distant.

**Conséquence concrète, mesurée sur les deux seuls nœuds distants disponibles** :
- PC3 (`10.40.13.2`, deux GPU NVIDIA réels, **sans** `docker`) → rapporté `docker ✓`.
- PC4 (`192.168.1.161`, GPU AMD uniquement, **sans** NVIDIA) → rapporté `nvidia ✓` (faux) **et**
  `docker ✓` (faux).

C'est l'inverse exact de la philosophie « Discovery + Adoption » du projet : un faux positif
pousserait à **adopter une infrastructure qui n'existe pas**, plutôt que de réinstaller à tort.

**Portée, corrigée par la revue d'architecture** : `SshRunner.run()` est une primitive partagée
par ~20 sites d'appel. Ma mesure initiale (limitée aux **espaces**) avait manqué un **second
défaut vivant** : `discover.py:85-87` interroge `docker ps --format {{.Image}}|{{.Names}}|
{{.Ports}}` — aucun espace dans le motif, donc invisible à ma mesure, mais le `|` non protégé
redevient un **vrai pipe shell** une fois aplati par SSH. Vérifié :

| | rc | sortie |
|---|---|---|
| argv actuel (aplatissement naïf) | **127** | `sh: 1: {{.Names}}: not found` |
| même argv, `shlex.join` | **0** | liste réelle des conteneurs |

**La découverte de conteneurs distants via SSH ne renvoyait donc RIEN, silencieusement, depuis
toujours** — un défaut plus grave que la troncature de `discover.py:80` (échec silencieux d'un
pipeline plutôt qu'un script tronqué). Le même correctif de primitive le répare ; ce n'est pas
laissé comme effet de bord non prouvé (voir G6).

`shlex.quote` se déclenche sur bien plus que l'espace (tout hors `[\w@%+=:,./-]`) : la revue a
vérifié chaque appelant réel du dépôt un par un. Tous les autres (`kubectl get nodes -o json`,
`cat /proc/meminfo`, `lscpu -J`, `nvidia-smi --query-gpu=... --format=csv,noheader,nounits`,
`helm ... --repo https://...`, `ollama pull qwen2.5-coder:1.5b`, …) n'utilisent que des
caractères shell-sûrs : la chaîne transmise à SSH reste identique caractère pour caractère.
Un cas latent noté (`keys.py:30`, passphrase vide `-N ""`) tourne aujourd'hui exclusivement en
`SubprocessRunner` local, donc hors du fil SSH — non exposé en pratique, sécurisé en creux par
le même correctif si un jour il l'était.

## 2. Décision de conception

### Réfutation — « corriger seulement `discover.py`, éviter le motif `$1` »
Insuffisant : tout script multi-mots passé à `sh -c` retombe dans le même piège, quelle que soit
la façon de l'écrire (vérifié : `["sh","-c","command -v docker"]`, sans le trick `$1`, produit
la même troncature — `-c` ne reçoit que le premier mot `command`). Le défaut est structurel à
`SshRunner`, pas au style d'un appelant.

### Décision — re-quoter l'argv en un seul jeton shell dans `SshRunner.run()`
`shlex.join(argv)` avant l'envoi, passé comme **unique** élément après `--` (au lieu d'étendre la
liste). OpenSSH n'a alors plus qu'un seul élément à transmettre : aucun aplatissement possible.
Le shell distant reçoit une chaîne correctement quotée et la reparse en un argv identique à
l'original — exactement le comportement déjà correct de `SubprocessRunner`.

**Non-régression, énoncée précisément après la revue d'architecture** (l'affirmation initiale
« identique pour TOUT appelant » était trop large — réfutée par le cas `docker ps --format`
ci-dessus) : pour tout appelant dont les éléments d'argv ne contiennent que des caractères
shell-sûrs (`[\w@%+=:,./-]`), la chaîne transmise reste identique caractère pour caractère.
Vérifié un par un sur chaque appelant réel du dépôt. Le seul appelant hors de cet ensemble sûr
et réellement exposé au fil SSH (`discover.py:85`) voit son comportement **corrigé**, pas
seulement préservé — changement souhaité, prouvé par un test dédié (G6).

## 3. TDAD

- **G1** — pour un argv multi-mots (le cas cassé), un seul élément subsiste après `--` dans la
  commande construite : rien à aplatir.
- **G2 (le détecteur du défaut)** — cet élément unique, rejoué à travers un **vrai** `/bin/sh -c`
  local (reproduisant exactement ce que ferait le shell distant, sans réseau), distingue
  correctement un binaire présent d'un binaire absent. Sur le code actuel : les deux se
  confondent (rc=0 dans les deux cas) ⇒ rouge.
- **G3** — non-régression : pour chaque argv simple déjà utilisé par un appelant réel du dépôt
  (`kubectl get nodes -o json`, `cat /proc/meminfo`, `lscpu -J`, `nvidia-smi -L`, …), la commande
  construite après correctif est **identique caractère pour caractère** à avant.
- **G4** — le chemin réel : `discover.py` avec un `SshRunner` dont la commande est interceptée,
  pour un binaire présent et un binaire absent, distingue correctement les deux.
- **G6** — le second défaut (`docker ps --format` avec `|` non protégé) est réparé, pas
  seulement laissé en effet de bord : rc=127 avant, rc=0 après, sur le vrai motif du dépôt.

Mutation à prouver : revenir à l'extension naïve de liste → G2 rougit.

## 4. Critères d'acceptation

- **CA1** `node discover` distingue correctement un binaire présent d'un binaire absent sur un
  nœud distant réel.
- **CA2** zéro régression : commande SSH construite identique pour tout appelant à argv simple.
- **CA3** le correctif vit dans `SshRunner.run()`, pas dans chaque appelant.
- **CA4** suite complète verte, couverture ≥ 85 %.

Rejoué en direct contre PC3 (NVIDIA, sans docker) et PC4 (AMD, sans docker), accès SSH par clé
avec empreinte SHA256 vérifiée (SSH-007) :

|---|---|---|

## 6. Preuve rejouée sur PC3 réel, après correctif

`inventaire()` (chemin réel de `forgeai node discover`) contre PC3, matériel physiquement
vérifié (deux GPU NVIDIA, sans `docker`) :

| Signature | Avant | Après | Vérité terrain |
|---|---|---|---|
| `docker` | ✓ (faux) | **✗** | absent (confirmé par SSH manuel) |
| `nvidia` | ✓ (vrai par coïncidence) | **✓** | 2× GPU NVIDIA réels |
| `kubectl` | ✓ | **✓** | présent (confirmé) |

Sur PC4 (AMD, sans docker ni NVIDIA), le même défaut donnait `nvidia ✓` **faussement** avant
correctif — écart le plus grave mesuré, puisqu'il aurait orienté une décision de placement GPU
vers le mauvais vendor sur un nœud réel.
