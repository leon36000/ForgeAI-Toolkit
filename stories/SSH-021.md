# SSH-021 — Appliquer la validation SSH canonique au bootstrap de nœud (fin du TOFU résiduel)

- **Issue** : #227
- **Tier** : T2 (sécurité — élimination du TOFU SSH résiduel dans l'ajout de nœud)
- **Dépend de** : SSH-007 (enrôlement d'empreinte dans `remote_probe.SshRunner`, mergé).
- **Reprise lane CODEX** (Codex retiré).
- **Périmètre fichiers** : `src/forgeai/network/remote_probe.py` (extraction du helper canonique),
  `src/forgeai/network/node_add.py` (adoption), `src/forgeai/cli.py` (`_node_add` + `--hostkey`),
  `src/forgeai/web/server.py` (`POST /api/nodes` : `hostkey` requis + passé au bootstrapper),
  `tests/test_ssh021_nodeadd.py` (nouveau), `stories/SSH-021.md` (+ tests existants mis à jour :
  test_node_add, test_web_nodes — nouvel argument requis).

## 1. Vulnérabilité résiduelle (code réel)

SSH-007 a supprimé le TOFU de `remote_probe.SshRunner`. Mais `network/node_add.py` `SshBootstrapper`
conserve DEUX sites `StrictHostKeyChecking=accept-new` (TOFU) :
- `install_key` (l.43) : `sshpass -e ssh-copy-id -o StrictHostKeyChecking=accept-new user@ip` — 1er contact
  avec un nœud neuf, mot de passe éphémère, fenêtre MITM.
- `verify_key` (l.59) : `ssh -o StrictHostKeyChecking=accept-new … true` — bascule clé.

L'opérateur qui provisionne le nœud (mot de passe éphémère, console) peut ET DOIT fournir l'empreinte
d'hôte à l'avance, exactement comme SSH-007.

## 2. Décision d'architecture

1. **Helper canonique** — extraire la logique d'enrôlement de `SshRunner._enroll` (SSH-007) en une
   fonction module-level de `remote_probe.py` :
   `enroll_hostkey(host: str, hostkey_sha256: str, timeout_s: float = 20.0) -> str` qui retourne le chemin
   d'un known_hosts temporaire (0600) contenant la clé offerte DONT l'empreinte SHA256 == `hostkey_sha256`,
   sinon lève `RemoteProbeError`. `SshRunner._enroll` DEVIENT un appel à ce helper (comportement inchangé,
   prouvé par les tests SSH-007 existants). *Justif :* une seule implémentation « canonique » réutilisable,
   pas de duplication ; refactor sans régression.
2. **Adoption dans `node_add.SshBootstrapper`** — `__init__(timeout_s, hostkey_sha256)` : empreinte REQUISE
   (validée « SHA256: » avant tout réseau, comme SSH-007). `install_key`/`verify_key` appellent
   `enroll_hostkey(ip, self.hostkey_sha256)` → known_hosts temp, puis passent
   `-o StrictHostKeyChecking=yes -o UserKnownHostsFile=<temp>` à `ssh-copy-id`/`ssh` (plus jamais accept-new).
   Nettoyage du temp en `finally`. *Justif :* même modèle anti-MITM que SSH-007 sur le 1er contact.
3. **`add_node`** propage `hostkey_sha256` au bootstrapper (via `SshBootstrapper(hostkey_sha256=…)` construit
   par l'appelant, signature `add_node` inchangée puisque le bootstrapper est injecté).
4. **CLI `_node_add`** — nouvel arg `--hostkey SHA256:…` (requis, cohérent avec `node tailscale`/`node probe`) ;
   construit `SshBootstrapper(hostkey_sha256=args.hostkey)` ; capture aussi `RemoteProbeError` → code 12.
5. **Web `POST /api/nodes`** — `hostkey` ajouté aux champs requis (400 « champs manquants » sinon) ; passé à
   `SshBootstrapper(hostkey_sha256=…)`. *Justif :* le durcissement s'applique à TOUT chemin d'ajout de nœud (CLI + web).
6. **Hors périmètre** : rotation de clés, known_hosts hashé, MD5 legacy (SHA256 seul).

## 3. Stratégie TDAD (`tests/test_ssh021_nodeadd.py` — RED d'abord)

Mock de `subprocess.run` par dispatcher argv[0] (ssh-keyscan/ssh-keygen/ssh-copy-id/ssh), comme SSH-007.
- **G1** `SshBootstrapper(hostkey_sha256="")` ou mal formée → `NodeAddError`/`RemoteProbeError` AVANT réseau.
- **G2** `install_key` avec empreinte qui MATCH la clé offerte → `ssh-copy-id` lancé avec
  `StrictHostKeyChecking=yes` + `UserKnownHostsFile=<temp>`, argv NE contient PLUS `accept-new`.
- **G3** empreinte qui NE MATCH PAS → refus, `ssh-copy-id` (commande d'install) JAMAIS lancée.
- **G4** `verify_key` : mêmes garanties (yes + known_hosts, pas d'accept-new).
- **G5** non-régression du helper : `enroll_hostkey` + `SshRunner` (tests SSH-007) restent verts (refactor sûr).
- **G6** CLI : `node add … ` sans `--hostkey` → code 12 / SystemExit (requis) ; le mot de passe reste hors argv (env).
- **Détectance** : muter `=yes`→`=accept-new` dans install_key/verify_key → un test tombe.

## 4. Critères d'acceptation

- **CA1** `accept-new` totalement supprimé de `node_add.py` ; toute connexion utilise `=yes` + known_hosts vérifié.
- **CA2** empreinte absente/mal formée → refus AVANT réseau ; empreinte ≠ offerte → refus, install jamais lancée.
- **CA3** `enroll_hostkey` est LE helper canonique, appelé par `SshRunner` (SSH-007) ET `SshBootstrapper` ; pas de duplication.
- **CA4** `node add` exige `--hostkey` ; mot de passe éphémère jamais en argv (env, inchangé).
- **CA5** suite complète verte (dont tests SSH-007 non régressés), no-stub, couverture ≥ 85 %.

## 5. Risques

- `ssh-keyscan` indisponible au 1er boot du nœud → enrôlement échoue proprement (refus, pas de TOFU).
- Refactor de `SshRunner._enroll` : couvert par les tests SSH-007 existants (non-régression G5).
- `sshpass`/`ssh-copy-id` absents → échec clair (hors périmètre, comportement pré-existant).
