# D4 — L'écran d'inventaire : l'utilisateur voit et choisit

## Défaut (prouvé, reviews/D4/evidence/RED.txt)

Le back-end sait tout faire — `/api/discover` exposée (D1), `adopt` validé et propagé (D3),
adoption appliquée au rendu (D2). **L'interface n'en utilise rien :**

    appels à /api/discover dans app.js    : 0
    occurrences de 'adopt' dans app.js    : 0
    occurrences de 'adopt' dans index.html: 0

Trois stories livrées, prouvées, scellées — et la capacité reste **inaccessible à celui pour
qui elle a été construite**. L'utilisateur ouvre l'interface, le produit sait détecter son
redis et l'adopter, mais l'écran ne lui montre rien et ne lui demande rien.

## Méthode de preuve : le précédent du dépôt

`engine_filter.js` est le modèle établi ici : la **logique pure** vit dans un module JS séparé,
prouvée par Node (`tests/js/engine_filter.test.cjs`, assertions réelles, exit ≠ 0 si une casse) ;
le **rendu DOM** relève de la vérification navigateur. Son en-tête le dit : *« preuve locale
re-jouable, pas un badge »*.

D4 suit ce précédent plutôt que d'inventer un harnais.

## Critères d'acceptation (testables)

- **CA-1** : un module `adoption.js` expose une fonction pure qui, à partir de l'inventaire
  rendu par `/api/discover` et de la liste des briques du plan, retourne les services
  **adoptables** — c'est-à-dire détectés ET présents dans le plan. Un service détecté mais
  absent du plan n'est PAS proposé (l'utilisateur ne peut pas adopter ce qu'il ne déploie pas).
- **CA-2** : une fonction pure construit le dictionnaire `{nom: "hôte:port"}` à partir des
  choix cochés, au format exact qu'attend `/api/deploy` (prouvé en D3).
- **CA-3** : un service **sans endpoint exploitable** dans l'inventaire n'est jamais proposé —
  on ne peut pas adopter ce qu'on ne sait pas joindre.
- **CA-4** : aucune case cochée → le dictionnaire est **vide**, et le POST ne contient alors
  pas de champ `adopt` (équivalence stricte avec le comportement actuel).
- **CA-5** : l'écran déclare une étape d'inventaire dans `index.html`, et `app.js` appelle
  bien `/api/discover` — vérifié sur le fichier livré, pas sur une intention.
- **CA-6** : non-régression — le POST `/api/deploy` conserve tous ses champs existants
  (`stack`, `backend`, `confirm`, `bricks`, `models`, `embeddings`, `rag_node`).

## Ce que cette tranche NE fait PAS (limites assumées)

- **Pas de découverte multi-nœuds** : `/api/discover` ne supporte aujourd'hui que `node=local`
  (elle renvoie 400 sinon — vérifié). L'écran porte donc sur le nœud local.
- **Pas de preuve navigateur automatisée** : conformément au précédent du dépôt, le rendu DOM
  n'est pas testé par un runner headless (aucun n'est câblé au projet). La logique pure l'est.
- **Couverture réelle de la détection** : seules redis, qdrant et postgres ont une signature ;
  les 9 autres briques du catalogue ne sont pas détectables et n'apparaîtront pas.

## Tranche 1 — logique pure (CA-1 à CA-4)

`src/forgeai/web/assets/adoption.js` : deux fonctions pures, aucune dépendance, compatibles
Node et navigateur, sans mutation des arguments et **sans jamais lever** — une entrée
inattendue est écartée, pas interprétée.

`tests/js/adoption.test.cjs` : **10 cas, 10 verts, code de sortie 0**, sur le modèle de
`engine_filter.test.cjs`.

    ok  cas nominal : redis + qdrant détectés, valides, au plan -> 2 adoptables triés
    ok  docker détecté (binaire) mais endpoint null -> écarté
    ok  postgres non détecté -> écarté
    ok  redis détecté et joignable mais ABSENT DU PLAN -> écarté
    ok  endpoints malformés (4 formes) -> tous écartés
    ok  inventaire null / undefined / {} / {services:[]} -> [] sans plantage
    ok  construireAdopt : 2 cochés sur 3 -> mapping des 2 seuls
    ok  construireAdopt : aucun coché -> {} (objet vide)
    ok  construireAdopt : coché mais endpoint invalide -> ignoré
    ok  aucune mutation des arguments

### Contrôle de mutation

| Mutation | Effet mesuré |
|---|---|
| filtre « présent au plan » neutralisé | **1 cas en échec**, code de sortie 1 |
| validation d'endpoint neutralisée | **3 cas en échec** |
| tout restauré | 10/10, code 0 |

Deux tentatives de mutation antérieures ont échoué **silencieusement** — l'une cherchait un
`includes` que le code n'utilise pas (il indexe en O(1)), l'autre un espacement approximatif.
Elles rendaient « 10/10 verts », c'est-à-dire *le même résultat qu'un test qui détecte*.
Depuis, la substitution est **vérifiée effective** avant d'interpréter le verdict : un contrôle
de mutation qui ne mute rien conclut toujours à tort.

## Tranche 2 — l'écran (CA-5, CA-6)

- `app.js` : `briquesDuPlan()` (**source unique** partagée avec le POST), `chargerInventaire()`,
  `renderInventaire()`, et `adopt` ajouté au POST **uniquement s'il est non vide**.
- `index.html` : bloc d'inventaire avec titre, aide et conteneur.
- `fr.json` / `en.json` : 3 clés sous `["web"]`.

### Défaut de source corrigé à l'application

Le livrable passait `state.bricks` à `servicesAdoptables`. Vérification faite :
`state.bricks` contient les briques **disponibles** (chargées de `/api/bricks`), pas celles que
l'utilisateur a **cochées** — ces dernières viennent de `state.overrides[overrideKey()]`.
Sans correction, CA-1 (« on ne peut pas adopter ce qu'on ne déploie pas ») aurait été **faux**.
Corrigé par un helper `briquesDuPlan()` que le POST et l'écran partagent, pour que la source ne
puisse plus diverger.

### Deux régressions provoquées par un ajout PUREMENT ADDITIF

Aucun code supprimé ni modifié — seulement une section HTML et trois clés. Et pourtant :

    FAILED test_ui_7_etapes.py::test_selecteur_rag
    FAILED test_web_i18n.py::test_toutes_les_cles_utilisees_sont_traduites
    FAILED test_web_i18n.py::test_api_sert_toutes_les_cles_utilisees

- ma balise `</section>` fermait prématurément l'extraction d'un test qui découpe le HTML par
  `split("</section>")` -> remplacée par `<div>` ;
- mes clés à la racine du JSON étaient invisibles pour un test qui lit `["web"]` -> déplacées.

**Ces deux conventions ne sont écrites nulle part** : elles vivent dans les tests. Ce sont des
tests hérités, sans rapport avec l'adoption, qui me les ont apprises — pour la troisième fois
de la session. C'est ce qui rend « toujours la suite COMPLÈTE » non négociable.

**Suite finale : Node 10/10, Python code de sortie 0, zéro FAILED.**

## Revue scellée tour 1 : REJECT — 3 objections, toutes FONDÉES

DeepSeek APPROVE, Gemini APPROVE, **Grok REJECT**. Grok seul a vu que la chaîne n'était pas
branchée :

1. **CRITIQUE** — `adoption.js` **n'était pas chargé** par `index.html`. `app.js` référence
   `ForgeAIAdoption` 3 fois, dont dans le handler du POST : **`ReferenceError` au clic sur
   Déployer, pour TOUS les utilisateurs**, pas seulement ceux qui adoptent. J'allais merger une
   régression qui casse le déploiement.
2. **CRITIQUE** — `chargerInventaire()` définie mais **jamais appelée** : l'écran serait resté
   vide en permanence.
3. **MAJEURE** — rien ne re-rendait l'inventaire quand les briques cochées changent, alors que
   `servicesAdoptables` en dépend.

### Corrigé et prouvé PAR EXÉCUTION

    ordre réel des scripts : engine_filter.js -> adoption.js -> app.js
    globalThis.ForgeAIAdoption défini : servicesAdoptables, construireAdopt, endpointValide
    adoptables : qdrant@127.0.0.1:6333, redis@127.0.0.1:6379   (docker écarté : endpoint null)
    dict envoyé au POST : {"redis":"127.0.0.1:6379"}

Appels branchés : `chargerInventaire()` à l'arrivée sur l'étape de déploiement,
`renderInventaire()` après chaque changement de briques (re-filtre sans refetch).

### Test permanent de CHAÎNE + son propre défaut

`tests/js/chaine_adoption.test.cjs` (5 cas) fige ces garanties. Mutations :
script retiré -> code 1 ; appel commenté -> code 1 ; restauré -> code 0.

**Première version de ce test : NON détectante.** Elle comptait les occurrences textuelles de
`chargerInventaire()` — une ligne mise en **commentaire** la trompait. Un test écrit contre les
défauts de branchement souffrait du défaut qu'il dénonce : vérifier le texte au lieu du
comportement. Seul le contrôle de mutation l'a révélé. Corrigé : comptage sur lignes non
commentées, définition exclue.

**Suite finale : Node 15/15 (10 + 5), Python code de sortie 0, zéro FAILED.**
