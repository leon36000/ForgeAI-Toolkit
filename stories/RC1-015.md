# Story RC1-015 — Supprimer l'exclusion globale des fichiers Markdown du scan de secrets

## Identité

- **Issue :** #445 (`[RC1-015] Supprimer l'exclusion globale des fichiers Markdown du scan de secrets`)
- **Branche :** `fix/RC1-015-secrets-markdown-scan`
- **Source audit :** EXT-018

## Constat

`.gitguardian.yaml` excluait globalement `**/*.md` — `stories/`, `Docs/`, `CANON/`,
`evidence/reviews/**` (prompts, rapports, verdicts narrés en Markdown) n'étaient jamais analysés
par GitGuardian, même si une valeur sensible y apparaissait. Gitleaks (gate CI toujours actif,
indépendant de cette config) réduit déjà le risque, mais une couverture par un détecteur n'est
pas une preuve d'équivalence avec un autre (ensembles de règles, heuristiques et validation en
ligne diffèrent — voir `Docs/reference/secrets-scanning.md`).

## Vérification réelle avant toute décision

`ggshield` (CLI GitGuardian) n'est pas installé par défaut (`dependencies=[]` stdlib pur du
produit — outil de dev optionnel, cf. `scripts/governance/capabilities.py`). Installé dans un
**venv scratch isolé** (jamais dans l'environnement du produit) pour vérifier réellement, pas
supposer :

1. **`ggshield secret scan path` fonctionne SANS authentification** pour la détection par
   motifs locale (confirmé : `ggshield 1.53.0`, `ggshield secret scan path pyproject.toml` →
   `No secrets have been found`, exit 0 — aucune erreur d'authentification).
2. **Scan comparatif réel** : `ggshield secret scan path --recursive --yes` sur l'arbre complet
   du dépôt, avec puis sans `**/*.md` dans `ignored_paths` :
   - Sans exclusion : **1961 fichiers scannés**, 4 incidents.
   - Avec exclusion (config d'origine) : **1710 fichiers scannés**, 4 incidents — **identiques**
     (mêmes fichiers, `tests/test_rag_durci_e2e.py`, `tests/test_models_cloud.py`,
     `tests/test_web_nodes.py`, `tests/test_node_add.py`, tous `known: true`, sans rapport avec
     le Markdown, préexistants avant cette story).
   - **251 fichiers `.md` de plus scannés, zéro nouvel incident.**
3. **Preuve positive de couverture** (pas seulement une absence de faux positifs) : un
   identifiant de clé d'accès AWS de forme plausible mais **aléatoire** (préfixe standard + 16
   caractères alphanumériques majuscules générés par `random.choices` — délibérément pas la
   constante d'exemple officiellement documentée par AWS dans ses tutoriels, qui elle N'EST PAS
   détectée, probablement dénylistée comme bruit connu), placé dans un `.md` temporaire hors de
   tout chemin exclu, produit :
   ```
   >> Secret detected: AWS Keys
      Validity: Invalid
      Detector documentation: https://docs.gitguardian.com/secrets-detection/secrets-detection-engine/detectors/specifics/aws_iam
   ```
   `Validity: Invalid` confirme que GitGuardian a réellement interrogé l'API AWS pour vérifier
   que la clé inventée est inactive — pas une simple reconnaissance de forme. Cette preuve
   démontre qu'un Markdown ordinaire non exclu EST désormais réellement analysé.
4. **Grep manuel ciblé** (préfixes `sk-`/`ghp_`/`gho_`/`AKIA`, blocs `PRIVATE KEY`, JWT,
   affectations `password=`/`token=`/`api_key=` à haute entropie) <!-- proof:allow : exemple prose --> sur l'intégralité du corpus
   Markdown : 12 occurrences trouvées au total, toutes des valeurs de test explicitement fausses
   annotées (`FAKE_KEY`, `DO-NOT-LEAK`, `# proof:allow — valeur de test`) :
   - 11 dans `evidence/reviews/DATA-002/`, `evidence/reviews/DATA-003/` — packs de revue scellés
     historiques dont les octets sont dans la préimage d'un `prompt_sha256` (RC1-011/#441) :
     **jamais modifiés**.
   - 1 dans `stories/ERR-041A.md` (documentaire, pas un artefact scellé — corrigée par cette
     story, voir ci-dessous).

## Décision

**Retirer `**/*.md` sans exclusion de remplacement.** La preuve empirique (§ ci-dessus) montre
qu'aucune exclusion de sous-arbre n'est nécessaire — le corpus Markdown actuel est déjà propre
au regard des détecteurs réels de GitGuardian. Une exclusion `evidence/reviews/**/*.md` aurait
répété l'erreur initiale à une échelle réduite (nouveaux prompts/rapports jamais scannés) sans
bénéfice mesuré : les 11 occurrences historiques de valeurs factices n'y déclenchent déjà aucun
incident réel.

**`stories/ERR-041A.md` corrigée** (pas un artefact scellé, éditable sans risque) : le littéral
factice qui y était cité (préfixe `sk-test`, hex de 64) retiré de la prose, remplacé par une
référence à la constante `SK` du module de test réel (`tests/test_redaction.py:37`, déjà
annotée `# proof:allow`, déjà scannée car `tests/*.py` n'a jamais été exclu) — cette story
elle-même ne réintroduit donc pas le littéral qu'elle documente avoir retiré.

## Limite assumée

Documentée dans `Docs/reference/secrets-scanning.md` § « Limite assumée » : `ggshield` non
authentifié en local peut différer du gate CI `GitGuardian Security Checks` (intégration GitHub
App, accès dashboard) — pour la comparaison PRÉCISE « CLI locale non authentifiée » vs « gate CI
GitGuardian réel sur une PR », c'est ce dernier qui fait foi. Portée volontairement ÉTROITE :
ceci ne constitue PAS une affirmation de préséance générale de GitGuardian sur `gitleaks` — les
deux détecteurs restent complémentaires, `gitleaks` reste le filet de dernier recours pour tout
contournement du cliquet structurel de `.gitguardian.yaml`, un risque distinct de celui traité
ici.

## Round 1 — 1 objection mineure réelle corrigée (APPROVE 3/3, 0 bloquante)

`_LIGNE_CLE` (regex de repérage de la ligne `ignored_paths:`) exigeait que la ligne se termine
immédiatement après les deux-points — un commentaire YAML sur cette même ligne (motif déjà
présent ailleurs dans `.gitguardian.yaml`, ex. `secret:  # proof:allow — ...`) aurait fait
retourner une liste vide à `parser_ignored_paths`, masquant silencieusement une réintroduction
de `**/*.md`. Corrigé : le regex tolère un commentaire final. +1 test de régression. 18 tests
désormais.

## Round 6 — 1 bug réel supplémentaire corrigé, filet ajouté proactivement (GPT-5.6-Terra-Pro REJECT)

**Bug réel, 3e variante de la même classe** : une ligne vide OU un commentaire seul (pas en fin
d'item, sur sa propre ligne) entre deux items YAML valides de `ignored_paths` terminait aussi
prématurément l'analyse — YAML autorise ces deux formes au sein d'une séquence. Repro confirmée
avant correctif (item après ligne vide/commentaire jamais analysé, `**/*.md` non détecté).
Corrigé : `parser_ignored_paths` ignore désormais toute ligne vide ou commentaire-seul au sein
de la liste, sans y mettre fin. +2 tests de régression (ligne vide, commentaire seul).

**Filet textuel ajouté proactivement** (avant qu'un 4e round ne trouve une 4e variante) : après
3 lacunes réelles trouvées dans l'analyseur structurel en 2 rounds, `verifier()` compare
désormais AUSSI le texte brut du fichier aux littéraux guillemetés interdits (`"**/*.md"`,
`'**/*.md'`, `"*.md"`, `'*.md'`) — indépendamment du succès du parsing structurel. Détecte entre
autres la syntaxe YAML "flow" (`ignored_paths: ["**/*.md"]`, jamais rencontrée dans ce dépôt
mais valide YAML, hors de portée du parseur ligne-par-ligne). Ne confond pas un glob borné
légitime (`"evidence/reviews/**/*.md"`) avec le littéral interdit (recherche du littéral
guillemeté EXACT, pas du sous-texte nu `**/*.md`). +2 tests.

## Round 7 — 1 bug réel supplémentaire corrigé, filet renforcé (GPT-5.6-Terra-Pro REJECT)

**Bug réel, 4e variante** : le filet textuel du round 6 cherchait des littéraux GUILLEMETÉS
BRUTS (`"**/*.md"`), sans décoder les échappements YAML. Une valeur `"**/*.md"` (guillemets
doubles) est sémantiquement `**/*.md` pour tout parseur YAML conforme (spec `\uXXXX` = point de
code Unicode) — ni l'analyseur structurel (comparaison sur la valeur brute non décodée) ni le
filet textuel (recherche du littéral brut) ne la détectaient. Repro confirmée avant correctif.

Corrigé, plus profondément que les rounds précédents (pas un simple patch ponctuel) :
- `_decoder_echappements_yaml()` décode les échappements `\uXXXX`/`\xXX`/`\UXXXXXXXX` d'une
  valeur entre guillemets DOUBLES (les guillemets simples YAML ne supportent AUCUN échappement —
  jamais décodés), retombe sur la valeur brute si le décodage échoue (séquence invalide) sans
  jamais lever d'exception.
- `parser_ignored_paths` décode désormais chaque valeur entre guillemets doubles extraite.
- Le filet textuel est redessiné : au lieu de chercher des littéraux bruts fixes, il balaie
  TOUTES les chaînes guillemetées (simples et doubles) du texte, décode celles entre guillemets
  doubles, et compare chaque valeur DÉCODÉE à `est_exclusion_markdown_globale()` — plus robuste
  et plus simple que l'accumulation de cas particuliers des rounds précédents.
- +3 tests (échappement Unicode détecté, non-confusion avec un glob borné légitime, repli sur
  la valeur brute pour un échappement invalide/tronqué).

Limite assumée, documentée honnêtement : ce décodeur ne couvre PAS l'intégralité de la grammaire
YAML des chaînes entre guillemets doubles (ex. échappements exotiques hors du sous-ensemble
`\uXXXX`/`\xXX`/`\UXXXXXXXX` reconnu par le décodeur `unicode_escape` de Python) — fermer cette
classe de contournements de façon exhaustive exigerait un vrai parseur YAML, hors du périmètre
volontairement étroit de ce cliquet (`dependencies=[]` stdlib pur). Le gate reste un filet
raisonnable contre une réintroduction ACCIDENTELLE, pas une preuve d'imperméabilité adversariale
totale — cohérent avec le périmètre déjà assumé pour `check_md_packs.py` (RC1-011/#441).

25 tests à ce stade.

## Round 8 — 1 bug réel supplémentaire corrigé (GPT-5.6-Terra-Pro REJECT)

**Bug réel, 5e variante** : un item exprimé comme SCALAIRE BLOC YAML (`- >-` replié ou `- |`
littéral), dont le contenu réel vit sur la ligne SUIVANTE plus indentée (syntaxe YAML valide),
n'était pas détecté. `_LIGNE_ITEM` captait `>-` lui-même comme une valeur non guillemetée
littérale `'>-'`, puis la ligne de contenu réel (plus indentée, non-item au sens de la regex)
terminait la liste sans jamais être examinée. Le filet textuel du round 6/7 ne pouvait PAS
rattraper ce cas : un scalaire bloc est par nature non guillemeté, hors de portée d'un balayage
de chaînes guillemetées. Repro confirmée avant correctif :
`parser_ignored_paths` sur `- >-\n  **/*.md` renvoyait `['>-']`, `verifier()` renvoyait
`(True, [])` (conforme) alors que le fichier réintroduit sémantiquement `**/*.md`.

Corrigé au niveau structurel (seul niveau possible pour cette classe, le contenu n'étant jamais
guillemeté) : `_consommer_scalaire_bloc()` détecte l'indicateur bloc (`_LIGNE_ITEM_BLOC`,
tolère les variantes de chomping `-`/`+`/indicateur de profondeur numérique), consomme les
lignes suivantes plus indentées que le tiret comme contenu de l'item, les joint (jointure
simplifiée : lignes vides ignorées, séparées par un espace — suffisant pour un glob court sur
1-2 lignes, hors périmètre de modéliser l'intégralité du pliage YAML). `parser_ignored_paths`
reprend l'analyse normale immédiatement après le contenu consommé (pas de fin de liste
prématurée pour l'item suivant). +4 tests (replié `>-`, littéral `|`, non-confusion avec un
glob borné légitime en scalaire bloc, item suivant correctement analysé après consommation).

29 tests à ce stade. Aucun changement de comportement pour le fichier réel `.gitguardian.yaml`
du dépôt (toujours conforme, aucun scalaire bloc utilisé).

## Round 9 — 1 bug réel supplémentaire corrigé (GPT-5.6-Terra-Pro REJECT)

**Bug réel, affinement du round 8** : la grammaire YAML de l'en-tête d'un scalaire bloc (spec
8.1.1.1) autorise l'indicateur de profondeur (chiffre 1-9) ET de chomping (`-`/`+`) dans les
DEUX ordres — `>-2` (chomping puis profondeur) OU `>2-` (profondeur puis chomping), les deux
équivalents sémantiquement. `_LIGNE_ITEM_BLOC` du round 8 n'acceptait que le premier ordre.
Repro confirmée avant correctif : sur `- >2-\n  **/*.md`, la regex ne matchait pas, `_LIGNE_ITEM`
capturait `'>2-'` comme valeur littérale, la ligne de contenu réel n'était jamais consommée —
`verifier()` renvoyait `(True, [])` alors que YAML résout l'item en `**/*.md`.

Corrigé : `_LIGNE_ITEM_BLOC` énumère explicitement les 4 formes valides (`[+-][1-9]` / `[1-9][+-]`
/ `[+-]` seul / `[1-9]` seul, groupe entier optionnel) au lieu d'un `[+-]?\d*` qui n'admettait
qu'un seul ordre. +1 test (reproduction exacte du cas rapporté par le reviewer).

## Round 10 — 1 bug réel supplémentaire corrigé (GPT-5.6-Terra-Pro REJECT)

**Bug réel, 6e variante** : `\/` est un échappement YAML valide d'un `/` littéral — vérifié
empiriquement contre un vrai parseur (PyYAML), en donnant à `yaml.safe_load` un `.gitguardian.yaml`
minimal dont l'item `ignored_paths` unique porte l'échappement `\/` : le résultat résout bien
l'item en `**/*.md`. <!-- proof:allow : clé de schéma YAML dans une paraphrase, pas un secret réel --> L'ancien
décodeur (round 7), fondé sur `str.encode(...).decode("unicode_escape")` appliqué à la valeur
ENTIÈRE, ne reconnaît pas `\/` (absent du jeu d'échappements Python) et le laissait tel quel —
`"**\/*.md"` n'était donc jamais reconnu comme équivalent à `**/*.md`.

Corrigé par une REFONTE (pas un patch ponctuel `.replace("\/", "/")`, qui aurait introduit une
ambiguïté réelle) : `_decoder_echappements_yaml` substitue désormais chaque jeton d'échappement
en un seul passage gauche-à-droite (`re.sub` sur un motif énumérant `\uNNNN`/`\xNN`/`\UNNNNNNNN`
/`\/`/`\\`), jeton par jeton, plutôt que de décoder la valeur entière puis chercher `\/` a
posteriori. Un `\\` authentique (backslash échappé) consomme atomiquement ses 2 caractères et
redevient un unique `\`, laissant un `/` qui le suivrait comme jeton SÉPARÉ à l'itération
suivante — sans ce découpage atomique, `\\/x` (backslash littéral puis slash littéral) serait
indistinguable de `\/x` (slash échappé) après une substitution textuelle naïve. +2 tests
(échappement `\/` détecté, non-confusion `\\` + `/` séparés vs `\/` atomique).

32 tests à ce stade. Aucun changement de comportement pour le fichier réel `.gitguardian.yaml`
du dépôt.

## Round 11 — 1 bug réel supplémentaire corrigé (GPT-5.6-Terra-Pro REJECT)

**Bug réel, 7e variante** : un scalaire double-guillemets YAML peut s'étendre sur PLUSIEURS
lignes physiques via une continuation de ligne échappée (`\` immédiatement suivi d'un saut de
ligne) — vérifié empiriquement contre PyYAML : le saut de ligne ET l'indentation de tête de la
ligne suivante sont retirés SANS espace de remplacement. Ni l'analyseur structurel (ligne par
ligne par construction, ne peut par nature pas voir un item réparti sur plusieurs lignes) ni
l'ancien filet (`_CHAINE_DOUBLE_GUILLEMETS` sans `re.DOTALL` — `.` de `\.` ne matche pas `\n`)
ne le détectaient.

Corrigé au niveau du filet (seul niveau capable de voir la chaîne complète, le contexte
`ignored_paths` n'étant pas nécessaire à sa détection) : `_CHAINE_DOUBLE_GUILLEMETS` compile
désormais avec `re.DOTALL` (la chaîne peut s'étendre sur plusieurs lignes), et
`_ECHAPPEMENT_YAML` reconnaît le jeton de continuation `\` + saut de ligne + indentation de tête
(`\\\n[ \t]*`), mappé vers une chaîne vide — sans espace de remplacement, conformément au
comportement YAML réel. +2 tests (détection de la continuation via le filet, retrait correct de
l'indentation de la ligne suivante).

34 tests à ce stade. Aucun changement de comportement pour le fichier réel `.gitguardian.yaml`
du dépôt.

## Round 12 — 1 bug réel supplémentaire corrigé, nouvelle couche (GPT-5.6-Terra-Pro REJECT)

**Bug réel, 8e variante, catégorie différente des précédentes** : une ancre YAML (`&nom`)
définie AILLEURS dans le fichier, référencée par alias (`*nom`) au sein de `ignored_paths` en
syntaxe flow (`ignored_paths: [*nom]`), réintroduit sémantiquement l'exclusion globale sans
qu'aucun littéral `**/*.md` n'apparaisse dans le contexte `ignored_paths` lui-même — vérifié
empiriquement contre PyYAML. Ni l'analyseur structurel (qui ne suivait aucune ancre) ni le filet
de chaînes guillemetées (qui ne voit qu'un `*nom`, jamais une valeur littérale) ne pouvaient la
détecter.

Cette variante diffère des rounds 1-11 : ceux-ci concernaient tous une lacune dans l'analyse de
la représentation textuelle d'UN SEUL nœud (l'item `ignored_paths` lui-même — commentaires,
indentation, échappements, continuations). Les ancres/alias exigent de résoudre une RÉFÉRENCE
CROISÉE à travers le document entier. Évaluation de proportionnalité avant correctif : une
résolution GÉNÉRALE des ancres YAML (mappings entiers, fusions `<<:`, alias vers alias) sortirait
du périmètre volontairement étroit de ce cliquet (`dependencies=[]` stdlib, pas un vrai parseur
YAML) — mais une résolution BORNÉE aux seules formes qu'un alias référencé depuis
`ignored_paths` peut pointer (scalaire bloc ancré, chaîne guillemetée ancrée, scalaire nu ancré)
reste implémentable sans dépendance externe et ferme directement la lacune signalée.

Corrigé par une extension, pas juste un patch du filet (les alias sont structurellement non
guillemetés, hors de portée du filet textuel par nature — contrairement aux rounds précédents) :
- `_construire_table_ancres()` : balaie l'intégralité du fichier, construit
  `{nom_ancre: valeur_résolue}` pour les 3 formes bornées ci-dessus.
- `_LIGNE_CLE_FLOW` + `_decouper_liste_flow()` : reconnaît désormais `ignored_paths: [...]` sur
  une seule ligne (jamais géré avant round 12 — seul le filet textuel couvrait le cas guillemeté
  de cette syntaxe), découpe par virgules de premier niveau en respectant les guillemets.
- `_LIGNE_ITEM_ALIAS` : reconnaît `- *nom` en item de bloc (pas seulement flow).
- `_resoudre_jeton_item()` : résout alias/guillemets/scalaire nu pour chaque jeton flow.
- Un alias vers une ancre INDÉFINIE retombe sur le jeton brut (`*nom`), sans planter ni faux

## Round 38 — 1 bug réel corrigé, un `#` non guillemeté n'est pas systématiquement un commentaire (GPT-5.6-Terra-Pro REJECT)

cas « précédé d'un blanc ».
