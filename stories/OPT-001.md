# OPT-001 — Mémoïser les sondes matérielles et backends du serveur web (OBS-A060-1 / A061)

## Cause racine (mesurée, pas supposée)
`/api/detect` et `/api/summary` relançaient des SOUS-PROCESSUS (lscpu/lspci/nvidia-smi/df, puis
docker/kubectl) à CHAQUE requête. Profilage de `_summary_payload` sur machine rapide :
```
_hardware_report (avant cache) : ~940-1583 ms (croissant)
_available_backends            :  801.6 ms   <-- sondes docker/k3s + 3e détection redondante
cluster_status                 :   89.5 ms
chassis_ids                    :    0.5 ms
```
Conséquences prouvées : saturation ~8 clients (p99 > 1 s à 16, audit A061) et ÉCHECS CI SYSTÉMATIQUES
(`test_summary_nodes` : timeout client 10 s dépassé sur runner chargé — 3 PR bloquées).

## Changement
Un SEUL cache TTL (60 s) thread-safe, partagé par les deux chemins chauds :
- `_hardware_report()` : HardwareProfile mémoïsé (source unique des sondes) ;
- `hardware_json()` : sérialise le rapport caché (/api/detect) ;
- `_summary_payload` : consomme `_hardware_report()` au lieu de re-sonder ;
- `_available_backends()` : résultat mémoïsé + COPIE défensive ; reçoit `_CachedDetector` (adaptateur
  exposant `full_report()` depuis le cache) — supprime la 3e sonde matérielle redondante ;
- `_hardware_cache_clear()` : invalidation explicite des DEUX caches.

## Défauts trouvés PENDANT le développement (chacun par une vérification, pas une intuition)
1. Cache posé sur `hardware_json()` mais `/api/summary` restait lent -> `_summary_payload` appelait la
   détection EN DIRECT (2e chemin non caché).
2. Toujours ~600 ms -> profilage : `_available_backends` = 801 ms (jamais suspecté au départ).
3. **INTERBLOCAGE** : `_available_backends` appelait `_hardware_report()` en tenant déjà `_hardware_lock`
   (`threading.Lock` NON réentrant) -> tests figés. Corrigé en `RLock` + TEST ANTI-RÉGRESSION dédié
   (`test_backends_et_hardware_sans_interblocage`, échoue par timeout si un Lock simple revient).
4. `run_checks` attend un DÉTECTEUR (il appelle `.full_report()`), pas un profil -> adaptateur `_CachedDetector`.

## Preuves
- `_available_backends` : 330 ms (1er appel, sondes réelles) -> **0.00 ms** (appels cachés).
- `_hardware_report` caché : **0.0 ms**.
- RED : reviews/OPT-001/RED-reproduction.txt · VERT : reviews/OPT-001/GREEN-focused.txt.
- Suite COMPLÈTE verte (0 régression). `test_summary_nodes` (qui bloquait la CI) : vert 3/3.
- Perf : reviews/OPT-001/PERF-apres.txt.

## Correction (limite honnête)
Le cache a un TTL de 60 s : un hotplug GPU / une installation de driver n'est visible qu'après expiration
(ou via `_hardware_cache_clear()`). C'est le compromis assumé — l'alternative (sonder à chaque requête)
est précisément le défaut corrigé.

## Rollback
`git revert` -> retour aux sondes par requête (défaut connu, CI de nouveau instable).
