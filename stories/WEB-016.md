# WEB-016 — Rate limiting + protection anti-bruteforce

- **Issue** : #248 · **Tier** : T2 (sécurité — disponibilité + anti-bruteforce du jeton)
- **Dépend de** : WEB-015 (normalisation erreurs) — mergé.
- **Reprise lane CODEX** · **Périmètre** : `src/forgeai/web/ratelimit.py` (nouveau),
  `src/forgeai/web/server.py`, `tests/test_ratelimit.py` (nouveau),
  `tests/test_web016_ratelimit_integration.py` (nouveau), `stories/WEB-016.md`.

## 1. Problème (code réel)
Le serveur web (`ThreadingHTTPServer`, multi-thread) n'a AUCUNE limitation de débit. Sur un bind
non-loopback (`--host 0.0.0.0`), un attaquant réseau peut (a) marteler les routes (DoS léger) et
(b) bruteforcer le jeton Bearer via des 401 répétés sur `authorize_mutation`. `self.client_address[0]`
donne l'IP source.

## 2. Décision (design — deux couches)
1. **Rate-limit global** par IP (token-bucket) : lisse les rafales. **IP loopback exemptée** (l'UI
   locale sonde fréquemment ; usage légitime non pénalisé).
2. **Anti-bruteforce auth** par IP (fenêtre glissante des 401 → lockout) : compte les échecs d'auth ;
   au-delà du seuil → lockout temporaire. **S'applique aussi en loopback** — un déploiement derrière
   un proxy local fait apparaître tous les clients en `127.0.0.1` ; exempter la lecture (fréquente)
   mais pas l'anti-bruteforce (rare, critique) est le bon compromis. En déploiement local par défaut
   (loopback, sans jeton), aucun 401 n'est généré → aucun lockout de l'opérateur.
3. **Refus** = HTTP 429 + `Retry-After: <s>` + corps `{"error":"rate_limited","retry_after":N}` (RFC 6585 ;
   aucune fuite d'IP/état interne).
4. **Store** : dict `{ip: état}` sous un unique `threading.Lock` (serveur multi-thread), avec éviction
   paresseuse qui **ne supprime jamais un lockout actif** (sinon un attaquant réinitialise en saturant
   la table).
5. **Défauts** (surchargables `FORGEAI_RATE_*`) : 100 req / 60 s (bucket) ; 5 échecs / 600 s → lockout 900 s.
6. **Point d'application** : `_rate_gate()` en TÊTE de `do_GET` et `do_POST` (avant WEB-017 / `_guard_mutation`) ;
   `record_auth_failure(ip)` quand `_guard_mutation` renvoie 401. `RateLimiter` déterministe (horloge
   injectable) → testable sans `sleep`.

## 3. TDAD (RED d'abord)
- **`tests/test_ratelimit.py`** (unitaire, horloge factice) : bucket sous/au-delà du seuil, recharge
  après fenêtre, loopback exempt du bucket, lockout après seuil (actif même en loopback), expiration du
  lockout, échecs hors-fenêtre ne lockent pas, thread-safety (rafale concurrente), éviction préserve un
  lockout actif. Le test EST le détecteur (retirer le lock → course détectable ; ne pas armer le lockout → test tombe).
- **`tests/test_web016_ratelimit_integration.py`** (serveur live) : 429 + `Retry-After` hors loopback
  au-delà du seuil ; loopback jamais limité ; lockout anti-bruteforce (N × 401 → 429 même avec le bon
  jeton ensuite) ; neutraliser `_rate_gate` → le test 429 tombe ; `/api/health` unique → 200.

## 4. Critères d'acceptation
- **CA1** rate-limit global hors loopback : au-delà du seuil → 429 + `Retry-After` ; loopback exempt.
- **CA2** anti-bruteforce : `auth_max` échecs 401 par IP → lockout `lockout_s` (429), y compris loopback.
- **CA3** thread-safe (un Lock, aucune opération hors lock) ; mémoire bornée (éviction ne purge pas un
  lockout actif).
- **CA4** non-régression : trafic normal 200 ; WEB-017 et mutations intacts ; suite complète verte,
  couverture ≥ 85 %.
