# D3 — L'UI peut adopter : le choix Adopter/Redéployer atteint le plan

## Défaut (prouvé par exécution, reviews/D3/evidence/RED.txt)

D1 expose l'inventaire (`/api/discover`), D2 sait adopter (`ServiceSpec.adopted_endpoint`,
mergé sur main). Mais `/api/deploy` :

    champs REQUIS    : ["stack", "backend", "confirm"]
    champs OPTIONNELS: ['bricks', 'embeddings', 'models', 'node', 'rag_node']
    occurrences de 'adopt' dans web/server.py : 0

**Aucun champ ne permet de dire « ce service, adopte-le ».** L'utilisateur voit son redis dans
l'inventaire, le produit sait l'adopter, et l'interface ne lui offre aucun moyen de le demander.

Conséquence : le défaut que D2 corrige **reste entier pour tout utilisateur passant par l'UI**,
c'est-à-dire le parcours principal du produit. La capacité est livrée mais inatteignable —
**D2 sans D3 n'a pas d'utilisateur.**

## Exigence de sécurité (non négociable)

`adopted_endpoint` **atteint le YAML rendu**. Le champ vient désormais d'une **entrée réseau
publique**. Une valeur non validée à la frontière HTTP est une injection potentielle dans le
manifeste de déploiement.

`ServiceSpec.__post_init__` valide déjà strictement (7 codes de rejet prouvés en D2), mais
**la validation en profondeur ne dispense pas de la validation à la frontière** : l'API doit
rejeter en 400 avec un message clair, pas laisser une `ValueError` remonter en 500 — un 500
sur une entrée malformée est un défaut de contrat d'API.

## Critères d'acceptation (testables)

- **CA-1** : `POST /api/deploy` accepte un champ optionnel `adopt`, dictionnaire
  `{"<nom_service>": "<hôte:port>"}`. Absent ou `{}` → comportement **strictement inchangé**.
- **CA-2** : chaque endpoint fourni est **validé à la frontière** ; une valeur malformée
  (`"pasdeport"`, `"h:abc"`, `"h:0"`, `"h:70000"`, `"::1:6379"`) → **400** avec un message
  nommant le service fautif. **Jamais de 500.**
- **CA-3** : une clé `adopt` qui ne correspond à **aucune brique du stack** → **400** nommant
  la clé inconnue (une faute de frappe ne doit pas être silencieusement ignorée).
  Source des noms valides : `deploy_ids(load_stack(stack_id))` — vérifié, 72 briques pour le
  stack `agentique`. Il n'y a pas de « plan » à cette étape : la route lance un sous-processus.
- **CA-4** : `adopt` d'un type invalide (liste, chaîne, nombre) → **400**, pas 500.
- **CA-5** : non-régression — sans `adopt`, la réponse est identique à avant.

## Re-cadrage (constat fait à l'implémentation, puis CORRIGÉ)

**Premier constat** : `/api/deploy` ne construit aucun plan — elle lance un sous-processus
`python -m forgeai wizard --ci --backend … --node … --stack …`. J'en avais conclu qu'un flag
CLI `--adopt` était le prérequis manquant.

**Ce constat était à moitié faux.** En poursuivant la lecture du code, le canal existe déjà :

    contenu = {"bricks": bricks_sel, "models": models_sel, "embeddings": embeddings_sel}
    if rag_node is not None:
        contenu["rag_node"] = rag_node
    sel_path.write_text(json.dumps(contenu, ensure_ascii=False))
    cmd += ["--selection", str(sel_path)]

L'UI transmet déjà ses choix par un **fichier JSON de sélection**, et `rag_node` en est le
**précédent exact** : un champ optionnel ajouté au dictionnaire, lu côté `cli.py` par
`sel.get(...)`. Aucun flag CLI nouveau n'est requis — il suffit d'ajouter une clé `adopt`
au même fichier.

La conception retenue suit donc ce précédent plutôt que d'inventer un mécanisme parallèle :
serveur → `contenu["adopt"]`, wizard → `sel.get("adopt")` → `dataclasses.replace` sur les
services concernés.

## Ce que cette tranche NE fait PAS (limites assumées)

- **Pas de page HTML dédiée.** Cette tranche livre le **contrat d'API** ; l'écran d'inventaire
  avec cases à cocher est une story suivante. Sans le contrat, l'écran n'aurait rien à appeler.
- **Pas de proposition automatique.** L'UI devra croiser `/api/discover` et le plan pour
  suggérer les adoptions ; ici l'appelant fournit explicitement le dictionnaire.
- **Pas d'écran HTML** : cette tranche livre le contrat d'API et sa propagation ; les cases
  à cocher de l'écran d'inventaire sont une story suivante.
- **Couverture réelle** : seules redis, qdrant et postgres ont une signature de détection.

## Preuves

### Validation à la frontière — 3 niveaux

**Unitaire** (`_valider_adopt`) : 18/18 cas conformes — None, `{}`, valide, valide×2, 3 types
invalides, clé vide, clé non-str, service inconnu, valeur non-str, sans `:`, deux `:` (IPv6),
hôte vide, hôte avec espace, port non numérique, port 0, port 70000. Borne de 40 caractères
vérifiée sur une clé de 200.

**HTTP réel** (serveur monté via `build_server`, requêtes réelles) : 9/9 conformes,
**0 réponse 500**.

    adopt=["redis"]              -> 400  adopt doit etre un objet {service: hote:port}
    adopt="redis:6379"           -> 400  idem
    adopt=42                     -> 400  idem
    adopt={"inexistant":"h:1"}   -> 400  adopt : service inconnu 'inexistant'
    adopt={"redis":"h:abc"}      -> 400  adopt['redis'] : port non numerique
    adopt={"redis":"h:99999"}    -> 400  adopt['redis'] : port hors bornes
    adopt={"redis":"pasdeport"}  -> 400  adopt['redis'] : forme attendue 'hote:port'
    adopt={"redis":":6379"}      -> 400  adopt['redis'] : hote invalide
    stack inconnu                -> 404  stack not found   (pas transformé en 500)

**Permanent** : `tests/test_adoption_api.py`, 17 tests.

### Contrôle de mutation — le défaut est PROUVÉ, pas supposé

Validation neutralisée (`erreur_adopt = None`) :

    FAILED test_aucune_reponse_500_sur_entree_malformee[payload3-service_inconnu]
    FAILED test_aucune_reponse_500_sur_entree_malformee[payload4-port_non_num]
    FAILED test_aucune_reponse_500_sur_entree_malformee[payload5-port_hors_bornes]
    FAILED test_aucune_reponse_500_sur_entree_malformee[payload6-pas_de_port]
    FAILED test_aucune_reponse_500_sur_entree_malformee[payload7-hote_vide]

Restaurée -> 17 verts.

**Sans validation, l'API renvoie donc réellement des 500 sur une faute de saisie.** C'est ce
que la story annonçait ; c'est maintenant mesuré.

Nuance révélée par la mutation : les **types** invalides (liste, chaîne, nombre) ne
provoquaient pas de 500 — ils étaient **silencieusement ignorés**, l'adoption disparaissant
sans un mot. Deux défauts distincts, tous deux traités par la même garde.

## Preuve finale

**Couverture du code neuf : 37/37 = 100 %.** Suite complète : code de sortie pytest **0**.
**22 tests** dans `tests/test_adoption_api.py`.

### Piège de test évité (faux positif de ma propre sonde)

Les 3 tests du chemin nominal échouaient d'abord en accusant un code correct. Cause : la
fixture `server` neutralise `_DEPLOY_CMD`, ce qui **court-circuite le bloc `if cmd is None:`**
— celui-là même qui contient l'écriture du fichier de sélection. Le test ne pouvait donc
jamais observer ce qu'il prétendait vérifier.

Corrigé par une fixture `server_reel` qui laisse `_DEPLOY_CMD` à `None` (vrai chemin) et
neutralise le **spawn** (`subprocess.Popen`) au lieu de la commande. La justification est en
docstring : unifier les deux fixtures « pour simplifier » rendrait les 3 tests silencieusement
inopérants — verts, mais ne prouvant plus rien.

C'est RAG-005 sous une autre forme : **la neutralisation qui rend un test commode supprime le
chemin qu'il devait prouver.** Parade : neutraliser au plus près de l'effet de bord, jamais en
amont d'une décision.

### Régression détectée et corrigée

3 tests hérités (`test_deploy_persist.py`) sont tombés après ma modification : j'appelais
`deploy_ids(load_stack(stack_id))` **inconditionnellement**, alors que ces tests mockent
`load_stack` vers `None`. Défaut de ma spec — « valider » au lieu de « valider *s'il est
présent* ». Charger le stack sans `adopt` était un travail inutile ET un risque.

Ces tests ne concernent ni l'adoption ni la validation : ils protègent la persistance d'état.
C'est leur indifférence même au stack qui a révélé mon appel superflu.

## Défaut RÉEL de D2 découvert par D3 (majeur)

En écrivant le test du maillon wizard, le déploiement a échoué sur une garde inattendue :

    forgeai wizard --backend compose --selection <avec adopt>  ->  returncode 1
    stderr : "127.0.0.1 est inutilisable comme cible d'Endpoints depuis un pod"

Cause : `cli.py` appelait **`render_k3s` inconditionnellement**. Le wizard écrit toujours
`compose.yaml` ET `k3s.yaml`, quel que soit `--backend`. La garde `AdoptionNonSupporteeK3s`
livrée par D2 bloquait donc **le chemin compose** — celui-là même que D2 supporte.

**D2 est mergé sur main avec APPROVE 3/3, 100 % de couverture et 19 tests. Sa capacité
principale était pourtant inutilisable dès qu'on passait par le wizard**, c'est-à-dire
toujours en usage réel.

Pourquoi personne ne l'a vu : les tests de D2 appelaient `render_compose(plan)` et
`render_k3s(plan)` **séparément**, chacun dans son test. Aucun n'empruntait le chemin où les
deux sont appelés sur le MÊME plan. Trois vendors aveugles n'ont rien vu non plus — le pack
montrait des renderers corrects et des tests verts.

**Corrigé** : le manifeste k3s n'est rendu que si `--backend` est k3s/k8s, ou si le plan ne
contient aucun service adopté. Matrice prouvée par exécution du VRAI binaire :

| backend | adopt | code | k3s.yaml | comportement |
|---|---|---|---|---|
| compose | oui | **0** | non | l'adoption compose fonctionne (défaut corrigé) |
| compose | non | 0 | oui | non-régression |
| k3s | oui | **1** | non | garde D2 légitime : refuse |
| k3s | non | 0 | oui | non-régression |

## Note sur la couverture (faux négatif de l'outil)

Le bloc `if adopt:` de `cli.py` apparaît « non couvert » : les 3 tests qui l'exercent lancent
le wizard en **subprocess**, et `pytest-cov` ne suit pas les processus enfants.

Vérifié par mutation plutôt que par le compteur :

    bloc neutralisé (`if False:`) -> test_adopt_applique_au_plan     ROUGE
                                  -> test_adopt_service_inconnu_abort ROUGE
    restauré                      -> verts

Le code est donc bien exercé. **La couverture de ligne ne mesure pas ce qui traverse un
subprocess — et c'est précisément là que vivent les défauts de composition**, comme celui de
D2 ci-dessus.
