# OPT-002 — Borner les sondes du chemin web (suite d'OPT-001)

## Cause racine (mesurée)
`SubprocessRunner` borne chaque commande à **20 s** (`core/runner.py:22`) — légitime pour un DÉPLOIEMENT,
mais ce même défaut s'appliquait aux **sondes de LECTURE** déclenchées par une requête HTTP courte.
Le PREMIER appel (non caché) de `/api/summary` enchaîne lscpu, lspci, nvidia-smi, df (détection),
docker + kubectl (backends) et kubectl (cluster) : **une seule sonde lente** dépasse le budget de la
requête. Conséquence prouvée : `test_summary_nodes` échouait systématiquement sur runner CI (timeout
client 10 s), bloquant la merge-queue (#182, #184, #185). OPT-001 avait posé le cache — il n'aide qu'à
partir du 2e appel ; **le premier restait exposé**.

## Changement (minimal : 4 lignes)
- Constante `_PROBE_TIMEOUT_S = 3.0` (sondes du chemin HTTP).
- Appliquée aux **3 sondes de lecture** : `_hardware_report`, `_available_backends`, `cluster_status`.
- Les **5 autres** `SubprocessRunner()` du fichier (déploiement, ajout de nœud, inventaire) gardent les
  20 s : c'est justifié pour des opérations longues. Distinction explicite, pas globale.

## Preuves
- 3 tests RED (aucune borne dédiée, runners non bornés) -> verts.
- Bornage prouvé à l'exécution : `sleep 30` via le runner de sonde -> **coupé après 3.0 s** (vs 20 s).
- Suite COMPLÈTE verte (0 régression) ; no-stub OK (264) ; diff minimal (4 lignes).

## Note d'exécution (transparence)
Une première tentative de patch par découpage de tranches avait involontairement supprimé des fonctions
voisines (`_catalogue_entries_cached`, `_json_body`, `_read_data_text`) — détecté par les tests, corrigé
en repartant de `main` avec un patch CHIRURGICAL (substitutions de lignes exactes + assertions d'unicité).

## Rollback
`git revert` -> les sondes web reprennent le défaut 20 s (défaut connu : instabilité CI).
